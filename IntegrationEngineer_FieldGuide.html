Integration Engineer Field Guide

Colaberry Enterprise AI Leadership Accelerator — AI Solution Architect Track

You are not being trained to become a full-time integration engineer. You are being trained to direct, evaluate, and approve AI-generated integrations between systems that were never designed to talk to each other. This guide gives you the ~20% of integration engineering knowledge that produces ~80% of the judgment you need at review time: what a correct contract looks like, what a safe retry looks like, what a defensible failure path looks like, and what questions expose a shortcut an AI code generator took when nobody was watching.

How this guide is organized

Part 1 teaches the concepts. Part 2 applies them to one concrete initiative — ClaimsFlow AI, an AI-assisted claims intake system for a mid-size insurance carrier — and produces six real, downloadable deliverables an architect would actually review and sign off.

The Initiative: ClaimsFlow AI

Northfield Mutual, a regional property & casualty insurer, is replacing its manual First Notice of Loss (FNOL) intake process with ClaimsFlow AI — an integration layer that lets a claimant file a claim from a self-service portal and have it validated, triaged, and (for low-risk, low-value claims) auto-settled without a human touching it, while every claim that doesn't qualify is routed cleanly to a human adjuster. Every example, diagram, and document in this guide is built against this one initiative so nothing here is abstract.

Why this is a good teaching case

It has every seam an architect will ever have to review: a legacy system with no concept of idempotency (PolicyCore), a slow async AI vendor (DocScan AI), a fast synchronous AI vendor with strict SLAs (FraudLens AI), a payment system where duplicate calls mean duplicate money movement (SettlePay), and a fire-and-forget notification system (NotifyHub) where losing a message is embarrassing but not catastrophic. Six systems, four different risk profiles, one integration layer.

Why Integration Exists

No enterprise system was built to be the only system. PolicyCore knows nothing about fraud scoring. FraudLens knows nothing about deductibles. The Customer Portal knows nothing about SOAP. Integration is the discipline of making independently-owned, independently-changing systems cooperate on one business outcome — settle this claim correctly — without any one of them having to understand the others' internals. As an architect, your job is not to write the glue code; it's to make sure the glue code someone (or some AI) wrote will still be correct at 2 a.m. when FraudLens is slow, PolicyCore is down for maintenance, and the same webhook fires twice.

Review lens

If an AI-generated integration proposes GraphQL between two backend services purely because "it's flexible," push back — flexibility on an internal seam usually just hides which fields are actually load-bearing. Reserve GraphQL for a client that genuinely varies its query shape.

API Contracts & Versioning

A contract is a promise about shape, not implementation: request schema, response schema, error format, and behavior under bad input. Every seam in ClaimsFlow AI is versioned in the URL path (/v1/...) so PolicyCore's team can ship /v2/ without breaking the Hub mid-flight. Two rules matter more than any framework choice:

  • Additive changes never bump the major version. Adding an optional field to a response is safe. Removing a field, renaming a field, or changing a field's type is a breaking change — full stop, regardless of how "small" it looks in a diff.
  • A deprecated version stays alive for a published window (90 days minimum for this initiative) with both versions running in parallel and a deprecation header (Sunset) on every response.

Bad pattern to flag

An AI-generated PR that changes a response field's meaning (e.g., coverageLimit silently switching from dollars to cents) without a version bump. This is the single most common way "it worked in the demo" becomes a production incident.

Review lens

No secret ever appears in a URL query string (it ends up in access logs) or in a log line. Ask specifically: "show me where this token is logged" — an AI-generated logging statement that does log.info(request) on an object containing an Authorization header is a finding, not a nitpick.

Webhooks vs Polling

DocScan AI's OCR job can take 5–90 seconds depending on document count. The Hub does not poll it in a loop — it submits the job, gets a jobId back immediately (202 Accepted), and DocScan AI calls back a Hub webhook when done. This is a webhook pattern: push over pull.

Choose webhooks when

  • Completion time is unpredictable and can be long
  • The caller can expose a reachable, authenticated inbound endpoint
  • Near-real-time notification matters

Choose polling when

  • The caller cannot expose an inbound endpoint (e.g., behind strict outbound-only firewall rules)
  • The operation is short and bounded (PolicyCore lookups are sub-second, so a synchronous call, not polling, is used)
  • You need a simple fallback if webhook delivery is unreliable

Design note in this initiative

Webhook delivery is not guaranteed exactly-once — DocScan AI's own retry policy means the same completion webhook can arrive twice. The Hub's webhook handler is built idempotent (see Error Handling & Retry Design) and the Test Plan has an explicit duplicate-delivery case for exactly this reason.

Idempotency, Retries & Backoff

Idempotent means: calling the same operation twice with the same idempotency key produces the same end state as calling it once — no duplicate payment, no duplicate claim record. This matters most wherever money or a permanent record moves: SettlePay payments and PolicyCore claim writes both carry an Idempotency-Key header (a UUID generated once per business operation, stored by the Hub, and reused on every retry of that same operation).

Retries are only safe on operations that are either naturally idempotent (a GET) or made idempotent via a key. Retries use exponential backoff with jitter — fixed-interval retries synchronize failures across concurrent requests and can hammer a struggling downstream even harder.

Good pattern

Attempt 1 immediate, attempt 2 at ~500ms, attempt 3 at ~1.2s, attempt 4 at ~2.8s, attempt 5 at ~6s, then stop and dead-letter. Each delay randomized ±20% (jitter) so retries from many concurrent claims don't all land on FraudLens in the same instant.

Bad pattern to flag

An AI-generated retry loop with no cap ("retry until success") or no idempotency key on a payment call. Both are production incidents waiting to happen — the first is a resource-exhaustion risk, the second is a duplicate-money risk.

Timeouts & Circuit Breakers

Every outbound call in ClaimsFlow AI has an explicit timeout — never "whatever the default is." FraudLens must respond inside 2 seconds because it sits in the claimant's synchronous wait; PolicyCore, a slower legacy system, gets 5 seconds. No call is ever unbounded.

A circuit breaker sits in front of each downstream call. After a threshold of consecutive failures (5 failures in 60 seconds, in this initiative's design), the circuit trips open: the Hub stops calling that downstream entirely for a cooldown window and fails fast with a clear error, instead of piling up timeouts on a system that's already struggling. After the cooldown, the circuit goes half-open and lets a small number of test requests through; if they succeed, it closes; if they fail, it reopens.

Review lens

Ask: "what happens to the claimant's screen if FraudLens is down for ten minutes?" If the honest answer is "the request just hangs," the circuit breaker either doesn't exist or has no fallback wired to it. See Document 4 for the exact state diagram and fallback behavior in this initiative.

Data Mapping & Transformation

Every system in this initiative speaks a slightly different dialect for the same facts. PolicyCore returns deductibles in whole dollars as a string (a mainframe habit); SettlePay expects integer cents. FraudLens returns a raw model score from 0.0–1.0; the business wants a LOW / MEDIUM / HIGH enum. Data mapping is the explicit, documented, testable translation between these — never an implicit assumption buried in code. Document 5 is the full field-by-field map for this initiative; nothing in it is unsourced.

Rate Limits

FraudLens AI contractually caps Northfield at 50 requests/second with a 429 Too Many Requests response and a Retry-After header when exceeded. The Hub must (a) stay under the limit proactively with a token-bucket limiter sized below the vendor's ceiling, and (b) treat a 429 as a retryable-with-backoff condition, honoring Retry-After exactly rather than guessing. A 429 is not an error to alert an on-call engineer about at 3 a.m. — it is expected, governed traffic-shaping behavior, and the Test Plan verifies it is handled as such.

Error Handling & Dead-Letter Queues

When retries are exhausted, the failed operation does not vanish — it moves to a dead-letter queue (DLQ) with full context (original payload, claim ID, correlation ID, all attempt timestamps and error bodies) for manual triage or automated replay. A silent catch(e){} that swallows the error is treated in this repo as a production defect, not a nitpick — see Document 4's DLQ design.

Good vs Bad Integration

Good: the SettlePay call

Idempotency key generated once per claim-settlement attempt; 5s timeout; 3 capped retries with backoff on 5xx/timeout only (never on 4xx); circuit breaker; failure routes to manual adjuster queue with a claimant-facing "processing" message, never a stuck spinner.

Bad: a first-draft DocScan AI integration

Hub polls DocScan AI every 500ms in a tight loop with no backoff, no timeout on the overall job, and no idempotency check on the webhook — if DocScan AI redelivers, the Hub double-processes the same OCR result and can double-count extracted damage estimates.

KPIs

An integration layer is measured the same way any production service is: success rate (calls that complete without error), latency percentiles (p50/p95/p99, because averages hide the tail that ruins the claimant's experience), retry rate (a rising retry rate is an early warning of downstream degradation before it becomes an outage), and DLQ depth (a growing dead-letter queue means retries are losing to a systemic failure, not a transient blip). See the live KPI Dashboard section below for this initiative's current numbers.

The Architect's Review Lens

When an AI coding agent hands you a finished integration, run it through these questions before approving:

#QuestionWhat a bad answer looks like
1Does every outbound call have an explicit timeout?"It uses the library default"
2Is every retry capped, backed off, and jittered?A while-true retry loop
3Does every write carry an idempotency key?"We assume the network won't duplicate it"
4Is the contract versioned, and is the version bumped on breaking changes?Unversioned endpoint, or a "minor fix" that silently changes a field's meaning
5Where do failed operations go after retries are exhausted?"They just log an error"
6Does any secret appear in a URL, a log line, or an error message surfaced to the user?An Authorization header echoed in a debug log
7Is the webhook/callback handler idempotent against redelivery?No dedup check on the inbound event ID
8Is there a test for the failure path, not just the happy path?Only a 200-OK test exists

1. Base Path & Versioning Policy

All Hub-owned endpoints are served under https://api.northfieldmutual.com/claimsflow/v1. Version is expressed in the URL path. A breaking change (removed/renamed field, changed type, changed status-code semantics) requires a new major version (/v2) served in parallel with /v1 for a minimum 90-day deprecation window, advertised via a Sunset response header on every /v1 call once /v2 ships. Additive, backward-compatible changes (new optional field, new endpoint) ship into the current version without a bump.

6. Authentication Summary

See Authentication concept section for the full rationale. In short: claimant-facing calls use OIDC/JWT; Hub-to-internal-system calls use OAuth2 Client Credentials; Hub-to-vendor calls use a static API key plus an HMAC-SHA256 request signature computed over the body and a timestamp (rejecting requests more than 5 minutes old, to block replay). 1. Timeouts per Outbound Call

CallTimeoutRationale
Hub → PolicyCore5.0sLegacy system, historically slower; claimant is waiting but coverage must be certain

2. Retry Policy & Exponential Backoff Curve

All retryable calls (timeouts, 5xx, 429) use exponential backoff with ±20% jitter, capped at 5 attempts. Non-retryable errors (400, 401, 403, 404, 409) fail immediately — retrying a validation error just repeats the same failure.

Figure 5 — Backoff curve used by the Hub's retry client: 0ms, ~500ms, ~1.2s, ~2.8s, ~6.0s, each ±20% jitter. Attempt 5 failing routes the operation to the dead-letter queue rather than retrying indefinitely.

3. Circuit Breaker State Machine

Figure 6 — Applied to every synchronous downstream (PolicyCore, FraudLens AI, SettlePay). While OPEN, the Hub returns a fast, clear "processing delay" error instead of piling up timeouts.

4. Idempotency Key Design

AspectDesign
Key generationUUID v4 generated once by the Hub per business operation (e.g., one settlement attempt for one claim) — never regenerated across retries of that same operation
TransportIdempotency-Key HTTP header on the request to SettlePay and PolicyCore write endpoints
StorageRedis, key = idem:{operation}:{key}, value = response snapshot, TTL 24 hours
Behavior on replayIf the key is seen again with an identical payload, the stored response is returned without re-executing the operation; if seen with a different payload, the call is rejected 409 DUPLICATE_OPERATION
Webhook dedup (DocScan AI)Inbound webhook jobId checked against a processed-events table before acting; a redelivered webhook with an already-processed jobId is acknowledged 200 and dropped, not reprocessed

5. Dead-Letter Handling

  • DLQ store: claimsflow.dlq.v1 queue, retention 30 days, encrypted at rest (claim PII present)
  • DLQ record contents: original payload, claim ID, correlation ID, idempotency key, every attempt's timestamp and response body, the downstream system name
  • Alerting: DLQ depth > 10 for > 15 minutes pages the on-call integration engineer
  • Replay: a manual or scheduled replay job re-submits a DLQ record through the same idempotent code path — safe because the idempotency key travels with the record

6. Failure-First Design Answers (per Colaberry standard)

QuestionAnswer for this initiative
What happens if this fails?Retries per the backoff curve above; if exhausted, the operation moves to the DLQ and the claim is routed to a human adjuster with a clear claimant-facing status
Will it retry, and how?Yes for timeouts/5xx/429 only; exponential backoff with jitter, capped at 5 attempts
Recovery path if retries exhausted?DLQ entry + manual adjuster queue + claimant notification; on-call paged if DLQ depth crosses threshold
Explicit failure modes NOT handled?Total loss of the Hub's own database is out of scope for this document (covered by the platform disaster-recovery runbook, not this integration design)
