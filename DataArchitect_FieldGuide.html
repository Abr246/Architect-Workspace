The Scenario You Will Direct, Evaluate & Approve

Project Beacon — Meridian Auto Insurance

Meridian Auto Insurance is a mid-size regional auto carrier writing policies across 14 states. Today, policy issuance lives in PolicyAdmin (a legacy Postgres system), claims handling lives in a separate ClaimsSystem, and premium collection runs through a third-party PaymentGateway. Underwriting, Finance, and the state Departments of Insurance each pull numbers that don't reconcile, because each pulls from a different source with a different definition of "premium" or "open claim."

Project Beacon is the initiative to unify Policies, Claims, and Payments into one governed enterprise data warehouse — with a documented model, a single data dictionary, enforced quality rules, traceable lineage, and a retention policy that satisfies state insurance regulators. You are the AI Solution Architect on this initiative. You will not hand-write the pipeline code — an AI coding agent will. Your job is to direct what gets built, evaluate whether the generated model and pipeline are correct, and approve (or reject) the result before it touches production. The nine documents in this guide are the artifacts you use to do that.

Why this matters to you specificallyAn AI agent will happily generate a schema, a pipeline, and a dashboard in minutes. It will not tell you, unprompted, that it forgot a foreign key, left a PII field unclassified, or built a pipeline that double-counts claim payments on retry. That is the ~20% of data architecture this guide exists to teach: enough to catch it.

Foundations · 01

Conceptual, Logical & Physical Models

Every real data model is written three times, at three altitudes, and an AI agent that skips straight to the third one is the most common failure mode you will need to catch.

Conceptual model — business language, no columns, no types. For Beacon: "A Policyholder holds Policies. A Policy insures Vehicles and carries Coverage. A Claim is filed against a Policy." This is what you review with underwriting and claims leadership; if they can't read it, it's wrong.

Logical model — entities gain attributes, primary keys, and foreign keys, but still no vendor-specific types. This is where cardinality gets nailed down (see the next topic) and where you catch missing relationships before anyone writes SQL.

Physical model — the logical model made real in a specific engine: BIGSERIAL vs UUID, actual VARCHAR lengths, indexes, partitioning, constraint syntax. This is Document D3 in this guide.

Review lensIf an AI agent hands you a physical schema (DDL) with no logical model behind it, that is your first red flag — you cannot evaluate "is this the right shape" from CREATE TABLE statements alone.
Foundations · 02

Entities, Relationships & ERD Cardinality

An entity is one real thing worth tracking on its own — Customer, Policy, Vehicle, Claim. A relationship connects two entities and always carries a cardinality: how many of one side can relate to how many of the other.

Crow's-foot notation reads from the entity outward: a single tick means "exactly one," a circle means "zero (optional)," and the three-pronged "crow's foot" means "many." A Policy-to-Vehicle relationship drawn as 1 — ⋔ (one-to-many) means one policy can schedule many vehicles, but each vehicle row belongs to exactly one policy.

ReadingSymbolMeaning
One and only one—|—Exactly one related row is required.
Zero or one—o—The relationship is optional on this side.
One or many—⋔At least one related row, no upper bound.
Zero or many—o⋔The relationship is optional and unbounded.
Why you check this firstCardinality is the single fastest way to catch a wrong model. If an agent models Claim-to-Policy as one-to-one, every policyholder with two claims breaks the schema. See the full cardinality table in Document D1.
Foundations · 03

Normalization vs Denormalization

Normalization removes repeated and derivable data by splitting it into related tables, so every fact is stored exactly once. Denormalization deliberately re-introduces some repetition — usually by pre-joining or pre-aggregating — to make reads faster or simpler.

Normalized (OLTP)Denormalized (OLAP / reporting)
Exampleclaim, policy, customerfact_claim joined flat with policy & customer attributes
Optimized forSafe, fast writes; no update anomaliesFast reads; fewer joins for BI tools
Risk if done wrongSlow, join-heavy readsUpdate anomalies, storage bloat, drift between copies

The rule of thumb Beacon follows: normalize the source of record (OLTP), denormalize the read layer (OLAP) deliberately, through a controlled pipeline — never let denormalization happen by accident inside a transactional table.

Anti-pattern to flagA single "god table" with policy, vehicle, claim, and payment columns all in one row is not denormalization for performance — it's a missing model. Ask an agent to justify every denormalized table with a specific read pattern it serves.
Foundations · 04

OLTP vs OLAP, Warehouse vs Lake

OLTP (Online Transaction Processing) systems run the business moment to moment: PolicyAdmin writing a new policy, ClaimsSystem recording a payout. Rows are inserted and updated one at a time, normalized, and protected by ACID transactions.

OLAP (Online Analytical Processing) systems answer questions across millions of rows at once: "what was our loss ratio by state last quarter." They favor read speed over write speed, and are usually organized as a star schema — one or more central fact tables (measurable events: a claim, a payment) surrounded by dimension tables (the who/what/when/where: policy, customer, vehicle, date) that facts join out to.

A data warehouse holds structured, modeled, schema-on-write data curated for a known set of business questions — Beacon's warehouse is exactly this. A data lake holds raw or semi-structured data (schema-on-read) at lower cost, useful for data science exploration before a shape is known. Beacon lands raw extracts in object storage (lake-like) before modeling them into the warehouse — see Document D4.

Review lensIf a "warehouse" an agent designed has no dimension tables and every fact table repeats fifteen descriptive columns, it's a wide flat file wearing a warehouse's name — ask for the star schema.
Foundations · 05

ETL vs ELT & Pipelines

ETL (Extract, Transform, Load) transforms data in flight, before it lands in the target — the classic pattern when compute is expensive and the warehouse is fragile. ELT (Extract, Load, Transform) lands raw data first, then transforms it inside the warehouse using its own compute — the dominant pattern now that warehouses are cheap and elastic. Beacon uses ELT: raw extracts land untouched, then dbt-style SQL models transform them into the curated star schema.

A pipeline is not one step, it's a chain of stages, and the stage boundaries are where correctness is won or lost: extract (pull from source), validate (structural and quality checks), transform (clean, conform, model), load/publish (make visible to consumers). See the full staged design in Document D4.

The property you must always demand: idempotencyRunning the same batch twice — because a job retried, or someone re-ran a backfill — must produce the exact same end state, not duplicate rows. This is done with natural/idempotency keys and MERGE/UPSERT semantics instead of blind INSERT. A pipeline that "works the first time" but duplicates claim payments on retry is not done — it's a production incident waiting for a network blip.
Foundations · 06

Data Quality & Lineage

Data quality is checked along four recurring dimensions: validity (is the value well-formed — a real state code, a 17-character VIN), completeness (are required fields populated), uniqueness (no accidental duplicates on a key that should be one-per-entity), and consistency (do related facts agree — a claim's date of loss can't be after it was reported). Beacon's full rule set, with severity and the action each rule triggers, is Document D5.

Lineage answers a different question: for any number on a dashboard, where did it come from, through which transformation, from which source column? Without lineage, "why does the loss ratio look wrong" has no answer faster than reading every line of SQL in the pipeline. With it, you trace fact_claim.paid_amount straight back to claim_payment.amount in ClaimsSystem in one lookup — Document D8.

Review lensEvery field that appears on an executive dashboard should have a lineage row. A field you can't trace to a source is a field you can't defend to a regulator or an auditor.
Foundations · 07

Master Data & the Data Dictionary

Master data is the small set of core business entities that many systems need to agree on — at Beacon, that's the Customer identity. The Quote system, PolicyAdmin, and ClaimsSystem each capture a policyholder independently, sometimes with a typo'd name or an old address. Master Data Management (MDM) matches those records to a single golden record and gives every system a crosswalk back to it — detailed in Document D9.

Reference data (or code sets) are the small, shared, centrally-stewarded lookup lists everyone must use the same way: state codes, coverage types, claim statuses. If PolicyAdmin and the warehouse ever disagree on what code "CL" means, every downstream number is wrong.

The data dictionary is the contract that makes any of this auditable: every field, its type, its plain-English meaning, its source, whether it's required, and whether it's PII — Document D2. If a field exists in the warehouse but not in the dictionary, that's an orphan column, and it should not ship.

Foundations · 08

Governance, PII & Retention

Governance is the set of rules for who may access which data, under what conditions, for how long, and how it eventually gets deleted. It is not paperwork bolted on afterward — for an insurer, it is largely dictated by state Department of Insurance regulation and is as load-bearing as the schema itself.

PII (Personally Identifiable Information) must be classified field-by-field, not table-by-table: customer.city is not PII on its own, but customer.address_line1 is. Classification drives everything downstream — access tier, masking in BI tools, and retention clock. Beacon uses four tiers: Restricted, Confidential, Internal, Public — full definitions in Document D6.

Retention is a promise with an expiration date on both ends: data must be kept long enough to satisfy regulatory and legal-hold requirements, and deleted once that window closes — indefinite retention "just in case" is itself a compliance and security liability.

Review lensAsk an AI-generated schema one question per PII field: "what is its retention period, and what deletes it?" If the agent can't answer, the field isn't governed, it's just stored.
Foundations · 09

Schema Evolution

Schemas change — Meridian will add a new coverage type, or ClaimsSystem will add a field for subrogation recovery. The question is whether that change is backward-compatible: adding a nullable column or a new reference code is safe; renaming a column, changing a type, or making a nullable field required breaks every consumer that hasn't been updated in lockstep.

Two patterns keep evolution safe: additive-only changes in the OLTP source (never repurpose a column's meaning — add a new one), and Slowly Changing Dimensions (SCD Type 2) in the warehouse, which version a dimension row instead of overwriting it — so a policy's state at the time of a claim is preserved even after the customer later moves.

Review lensA pipeline that fails outright when a new, unexpected column appears in the source is safer than one that silently drops or misaligns it. "Fail loud on the unexpected" beats "guess and continue."

Good vs Bad Design, KPIs & the Review Lens

SignalGood designBad design
EntitiesOne entity per real-world thing, with a stable keyOne giant table mixing policy, vehicle, and claim columns
RelationshipsEvery relationship states its cardinality and is enforced by a FKRelationships implied by naming convention only, no constraint
Normal formNormalized where written (OLTP), denormalized only for known reads (OLAP)Denormalized everywhere "to be safe," or normalized in a reporting layer nobody can query
FieldsEvery field defined in the data dictionary and traceable to a sourceOrphan columns nobody can explain
PipelinesIdempotent, retried safely, quarantines bad rowsRe-running a job duplicates or silently drops data
PIIClassified per field, access-tiered, retention-datedPII mixed in with public fields, no access control

The KPIs that tell you whether Beacon's data foundation is healthy, independent of any single dashboard number: schema conformance rate (% of loaded rows matching the declared contract), data quality pass rate, lineage coverage (% of reported fields with a documented source), pipeline SLA adherence, and PII classification coverage (% of fields with a governance tag).

Your review checklist as AI Solution Architect1. Does the conceptual model match the business in plain language? 2. Does every relationship have a stated, enforced cardinality? 3. Is every field in the dictionary, with PII classified? 4. Is the pipeline idempotent and does it have a documented failure path? 5. Does retention have both a start and an end?

4. Deletion & Right-to-Be-Forgotten

A verified customer deletion request is logged immediately. Records under an active claim, a litigation hold, or a still-open regulatory retention window are carved out — they cannot be deleted early even on request; the customer is notified of the specific legal basis for the exception. Deletion executes automatically at the retention boundary via a scheduled job using a soft-delete-then-hard-delete pattern: records are tombstoned immediately and physically purged after a 30-day grace period, both steps idempotent and safe to re-run.

Forbidden patternDeleting a row and forgetting its downstream copies (a cached extract, a BI export, a backup) is a governance violation, not a technicality. Every deletion job must enumerate every place the record was propagated to.

Storage & Retention Strategy

Version1.0
StatusApproved for Build

Date2026-09-21

1. OLTP / OLAP Split

PolicyAdmin and ClaimsSystem (Postgres) remain the systems of record for transactional writes — small, fast, ACID-safe operations. The warehouse (columnar OLAP engine) is populated exclusively through the pipeline in Document D4 and is never written to directly by an application. Raw extracts land in low-cost object storage as an intermediate, lake-like layer before modeling.

2. Hot / Warm / Cold Tiering

TierAge windowStorageQuery SLAAccess pattern
Hot0–13 monthsWarehouse, compute-optimized, clustered on policy_id / claim_id< 5s p95Live dashboards, underwriting models, daily ops
Warm13–84 months (up to 7 yrs)Warehouse, partitioned, compressed, cheaper storage class< 60s p95Trend analysis, quarterly regulatory filings
Cold> 84 monthsArchived to low-cost object storage (not directly queryable)Restore-on-request onlyLitigation hold or audit request only; deleted at the 7-year boundary absent a hold

3. Tier Transition Logic

A nightly job moves fact partitions from Hot to Warm on their 13-month anniversary, and from Warm to Cold (archive) on their 84-month anniversary, unless a litigation-hold flag is present on the related policy or claim — in which case the record is pinned in its current tier and re-evaluated monthly. Both transitions are idempotent partition operations: re-running the job on an already-transitioned partition is a no-op.

Why this split, not "keep everything hot"Hot-tier compute is the most expensive resource in the stack. A claim closed six years ago is regulatorily required to exist, but nobody needs sub-5-second query time against it — cold storage meets the retention obligation at a fraction of the cost.

Master & Reference Data Definition

Version1.0
StatusApproved for Build

Date2026-09-21

1. The Golden Customer Record

A single policyholder can be captured independently by three systems, each with a slightly different spelling, address, or contact detail: the pre-bind Quote system, the post-bind PolicyAdmin system, and ClaimsSystem at First Notice of Loss. Master Data Management (MDM) resolves these into one golden record:

StepMethod
1. Deterministic matchExact match on (tokenized SSN, date_of_birth) — highest confidence, auto-merged.
2. Probabilistic matchFuzzy match on (name, date_of_birth, zip_code) for records without a usable SSN token; scores in the ambiguous band route to a human review queue rather than auto-merging.
3. SurvivorshipPolicyAdmin.customer_id is the golden/survivor key once a match is confirmed — it is the system of record for a bound policyholder.
4. CrosswalkQuote and Claims systems retain a mapping table (source_system, source_customer_id, golden_customer_id) so no source system is forced to change its own primary key.

2. Reference / Code Set Stewardship

Every code set has exactly one owner and one production table. A new code (e.g. a new coverage type for a usage-based-insurance pilot) requires steward approval before it ships to any system — this is what keeps PolicyAdmin, ClaimsSystem, and the warehouse from ever disagreeing on what a code means.
