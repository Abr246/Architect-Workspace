The Worked Example

MedSlot — AI-Assisted Scheduling & Triage, for Meridian Health Partners

Every document in this guide is written against one concrete, believable system so you can see what a real DevOps deliverable looks like rather than a generic template. Here is the system in one paragraph:

The Service
Meridian Health Partners operates 14 primary-care and urgent-care clinics across two states, with roughly 340 clinicians and 2,800 patient appointments booked per day. MedSlot is the patient-facing web and mobile-web application that lets patients describe symptoms in plain language, routes that description through an AI triage service to recommend the right appointment type and urgency tier, finds the next matching slot across the clinic network, and confirms the booking back into the clinics' EHR system over an HL7/FHIR interface. A booking that fails to reach the EHR, or a triage recommendation that silently returns the wrong urgency tier, has real clinical consequences — which is exactly why this is a good teaching example for an AI Solution Architect: the system is AI-assisted, patient-facing, integrated with a regulated system of record, and cannot be allowed to fail quietly.

System shape

  • Frontend: React SPA served via CloudFront/S3, mobile-web first
  • API: Node.js/Express booking-api, stateless, horizontally scaled on Kubernetes (EKS)
  • AI Triage Service: separate deployable, calls an LLM for symptom intake and urgency classification, returns a structured recommendation
  • EHR Adapter: HL7/FHIR translation layer to the clinics' EHR system of record
  • Data: PostgreSQL (bookings, slots, audit trail), Redis (session cache, idempotency keys, triage queue)

Why it's a good DevOps teaching case

  • Three services with different risk profiles need three different deployment strategies
  • A regulated downstream system (EHR) makes rollback and idempotency non-negotiable
  • An AI component (triage) can degrade in quality without crashing — monitoring has to watch for that, not just uptime
  • Real SLOs with real numbers, not "100% uptime" fantasy targets
The Discipline

Why DevOps Exists

Before DevOps, "build" and "run" were different teams with different incentives: developers were rewarded for shipping features, operators were rewarded for nothing breaking. Every release became a negotiation, then a 2 a.m. phone call. DevOps collapses that boundary into one accountable loop — the people who write the change also own its path to production and its behavior once it's live.

For an AI Solution Architect, the stakes are higher, not lower: an AI engineering agent can now write the pipeline, the infrastructure code, and the monitoring config as fast as it writes the feature. That speed is only safe if someone who understands the discipline is reviewing the result. You are that someone. You don't need to write the Terraform — you need to know a dangerous Terraform plan when you see one.

The risk this guide addresses
An AI agent will happily generate a pipeline that looks complete and is missing a rollback path, or a monitoring plan with an SLO of "100% uptime" that no real system has ever hit. Neither failure is visible by reading the code quickly. Both are visible once you know what to check for — which is the entire point of the next section.

The 20% to Know

You do not need to be able to write a Kubernetes manifest from scratch. You need to recognize whether one is complete. This guide covers nine ideas; together they are the 20% that explains nearly all the delivery and operations decisions you'll be asked to approve:

  • CI/CD pipelines — the automated path from commit to production
  • Build / release / run separation — why a running container never gets patched in place
  • Infrastructure as Code — environments defined in version-controlled text, not clicked together
  • Environments & parity — dev, staging, and prod should differ in scale, not in shape
  • Deployment strategies — blue-green, canary, rolling, and when each earns its complexity
  • Rollback — the undo button every release must have before it ships
  • Monitoring, SLIs, SLOs, error budgets — turning "is it working" into a number
  • Incident response & runbooks — what happens in the first five minutes of a bad page

Plus one lens that ties them together: the twelve-factor idea — a short list of properties that make software deployable at all.

CI/CD Pipelines

Continuous Integration means every change is automatically built and tested the moment it's proposed, so integration problems surface in minutes, not weeks. Continuous Delivery means every change that passes CI is automatically packaged into a releasable artifact; Continuous Deployment goes one step further and pushes that artifact to production automatically, with no human in the loop, when every gate passes. Most regulated or clinically-adjacent systems — MedSlot included — use Continuous Delivery with a human approval gate before production, not full Continuous Deployment.

Figure 1 — The MedSlot CI/CD Pipeline

Two human approval gates (Eng Lead before staging, Release Manager before prod); every later stage re-uses the exact image pushed in stage 5 — nothing is rebuilt. Full detail in Document 1 — CI/CD Pipeline Design.
Build / Release / Run separation
Build turns source code into a container image. Release combines that image with environment-specific config (which database, which feature flags) to produce something deployable. Run executes that release. The discipline: a release is immutable once created, and the same build artifact is promoted through dev → staging → prod unchanged — only the config around it differs. If an AI agent's pipeline rebuilds the image at each environment, that is a defect: you have lost the guarantee that what you tested is what you shipped.

Infrastructure as Code

Infrastructure as Code (IaC) means environments — networks, clusters, databases, caches, DNS — are defined in version-controlled text (Terraform, in MedSlot's case) and created by applying that text, never by a human clicking through a cloud console. This gives you three things a clicked-together environment cannot: a diff you can review before it takes effect, a history of who changed what and why, and the ability to recreate the exact same environment from scratch if it's destroyed.

What good IaC review looks like
Every change to shared infrastructure ships as a pull request with a terraform plan output attached, reviewed before terraform apply. State is stored remotely (S3 + DynamoDB lock) so two people can't apply conflicting changes at once. Secrets are referenced from a secrets manager, never written as literal values in the .tf files.
What to reject
A plan that shows a destroy-and-recreate of the production database because a field changed that should have been a non-destructive update. A module with hardcoded account IDs, API keys, or hostnames. Any apply run directly against prod without a plan reviewed first.

See Document 2 — Infrastructure-as-Code Plan for the actual MedSlot Terraform module layout, including the architecture view of how the pieces fit together.

Environments, Parity & Containers

Three environments earn their keep for most systems: dev (fast feedback, shared or ephemeral), staging (production-shaped, used for final verification), and prod (real users, real data). Parity means dev, staging, and prod run the same shape of system — same container image, same services, same config structure — differing only in scale (instance sizes, data volume, traffic). A staging environment that "simulates" production by running a different, lighter stack is not staging; it is a guess.

Containers (MedSlot runs on Kubernetes/EKS) are what makes this parity practical: a container image is a sealed, reproducible unit that runs identically on a laptop, in CI, and in production, because the entire runtime — not just the code — is packaged together.

Figure 2 — Environment Promotion Map

One artifact, one hash, promoted across environments unchanged — only configuration and scale change. Full matrix in Document 3 — Environment Strategy.

A pipeline to reject
"Deploy directly to production, then watch for errors" is not a deployment strategy — it is a bet with patients as the stake. Any AI-generated deployment plan with no staged traffic shift and no automatic rollback trigger should be sent back.

Rollback

A release without a tested rollback path is not finished — it is a one-way bet. Rollback has to answer three questions before a release ships, not after it breaks: what triggers it (a human decision, or an automated SLI breach), what it rolls back to (the last known-good artifact, by exact version), and is it safe for data — specifically, did the release run a database migration that the old code can no longer read?

The pattern that makes rollback safe
Database migrations ship in two steps across two releases: first an additive, backward-compatible change (new nullable column, new table) that both old and new code can tolerate; only once the new code is fully rolled out and soaked does a second release remove the old column. This is why MedSlot's rollback plan (Document 5) can always roll back the application without a corresponding database rollback.

See Document 5 — Rollback Plan for the exact triggers and target-version table used for MedSlot.

Monitoring, Logging, Alerting — SLIs, SLOs, Error Budgets

You cannot approve what you cannot measure. Three terms, in order:

  • SLI (Service Level Indicator) — a number you actually measure, e.g. "percentage of booking requests that complete in under 800ms."
  • SLO (Service Level Objective) — the target for that number, e.g. "99.5% of booking requests complete in under 800ms, measured over 30 days." No real SLO is 100% — that target has zero room for maintenance, dependency failures, or network blips, and chasing it burns engineering effort on the wrong problem.
  • Error budget — the inverse of the SLO, turned into an allowance you can spend: a 99.5% SLO allows 0.5% of requests to fail, which over 30 days of ~2,800 bookings/day is a concrete, trackable number of allowed failures (Document 7 does this arithmetic for all four MedSlot SLOs).
Why error budgets change the conversation
Once failure has a budget, "should we ship this risky change" becomes "do we have enough budget left this month" — a number, not a feeling. A team that has burned 90% of its error budget by day 10 should slow down and fix reliability, not ship more features. That is a policy decision an architect can enforce without reading a single log line.

Good monitoring also means alerting on symptoms, not causes — page someone when booking latency breaches SLO, not when CPU crosses an arbitrary threshold that may or may not mean anything to a patient. Every alert needs a named owner and a runbook link, or it is noise. Full detail in Document 6 — Monitoring & Alerting Plan and Document 7 — SLO / Error-Budget Sheet.

Incident Response & Runbooks

A runbook is a pre-written, step-by-step procedure for a specific known failure, written before the incident, not improvised during it. Good incident response has four parts: detect (the alert fires), triage (is this real, how bad, who needs to know), mitigate (stop the bleeding — often a rollback, not a fix), and resolve & review (root cause, and a blameless post-incident write-up that becomes a new protective test or alert). MedSlot's Deployment Runbook (Document 4) and Rollback Plan (Document 5) are both runbooks in this sense — they exist so that at 2 a.m., nobody is reasoning from first principles about a patient-facing scheduling outage.

The Twelve-Factor Idea

The twelve-factor app methodology is a short list of properties that make software deployable, scalable, and disposable in a modern cloud environment. You don't need all twelve memorized — you need the underlying idea: a well-built service holds no assumptions baked in that only work on one machine, at one point in time, with one human's secrets typed into it. In practice, the three that come up most often in review:

FactorWhat it means in review
Config separated from codeNo hostnames, credentials, or feature flags hardcoded — all come from environment variables or a config service
Stateless processesAny instance of booking-api can handle any request; session state lives in Redis, not in process memory
DisposabilityA pod can be killed and replaced at any moment without losing or corrupting a request in flight — this is what makes rolling deploys and auto-scaling safe

Good vs. Bad Delivery — A Quick Contrast

Good delivery looks like
  • Every release traceable to a commit, a pipeline run, and an approver
  • One artifact, promoted unchanged across environments
  • A rollback that takes seconds and has been tested, not just documented
  • Alerts tied to user-facing symptoms with a named on-call owner
  • An SLO with a real, defensible number and a tracked error budget
Bad delivery looks like
  • "We deployed by SSH-ing in and running git pull"
  • Secrets committed to the repo "temporarily"
  • No staging environment, or one that doesn't resemble prod
  • An SLO of "100% uptime" that nobody tracks against reality
  • An empty catch block where an error should have paged someone

The Architect's Review Lens

When an AI engineering agent hands you a pipeline, an infrastructure plan, or a monitoring config, run it through these six questions before you approve it:

  1. Is the artifact promoted, not rebuilt? The same image hash should appear in dev, staging, and prod logs.
  2. Does a rollback exist, and has it been exercised? "We can roll back" without a tested procedure is a hope, not a plan.
  3. Are secrets absent from code, config files, and logs? Check the diff for anything that looks like a key, token, or connection string.
  4. Do alerts page a named owner on a user-facing symptom? Not "CPU > 80%" with no owner attached.
  5. Is the SLO a real number with a tracked error budget? Reject "100% availability" on sight.
  6. What happens when this fails? If the plan doesn't answer that in writing, it isn't done — see Failure-First Design in this repository's own engineering rules.
This is the lens every document below was written to survive
Each of the eight MedSlot documents that follow answers all six questions explicitly. Use them as the reference shape for what "approved" should look like when an AI agent hands you the next one.

1. Purpose & Scope

This document defines the automated path from a developer's commit to running production traffic for all three MedSlot deployables: booking-api, triage-ai-service, and web-frontend. It is the controlling reference for pipeline changes; any modification to stage order, gates, or rollback behavior requires a PR against this document in the same change set as the pipeline code.

3. Quality Gates — Detail

  • Static analysis: ESLint (zero errors, warnings tracked not blocking), tsc --noEmit required clean per repository rule
  • Test coverage floor: 80% line coverage on any file touched by the PR; existing untested files are grandfathered per repository policy
  • Dependency & image scanning: Trivy scan on every built image; build fails on any Critical CVE, warns on High
  • Secret scanning: Gitleaks pre-commit hook + CI re-check; any match blocks the merge, not just warns
  • Contract check: OpenAPI schema diff between main and PR branch; a breaking change without a version bump fails the build
  • Idempotency check: integration suite runs every booking-creation test twice with the same idempotency key and asserts a single row is created

4. Branching & Promotion Model

Trunk-based development against main. Feature branches are short-lived (target < 2 days open). Release candidates are not separate branches — the artifact built from the merge commit to main is the one and only candidate, and it is the same binary promoted through Dev → Staging → Prod (see Figure 2, Document 3). There is no "cherry-pick to release branch" step, which removes an entire class of "it worked in staging but staging had a different build" incidents.

5. Pipeline Definition (abridged)

name: medslot-booking-api-ci
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npm test -- --coverage --coverageThreshold='{"global":{"lines":80}}'
      - run: npx gitleaks detect --no-git -v

  build-and-push:
    needs: verify
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t $ECR_REPO:${{ github.sha }} .
      - name: Scan image
        run: trivy image --exit-code 1 --severity CRITICAL $ECR_REPO:${{ github.sha }}
      - name: Push to ECR
        run: docker push $ECR_REPO:${{ github.sha }}

  deploy-dev:
    needs: build-and-push
    uses: ./.github/workflows/deploy.yml
    with: { environment: dev, auto_promote: true }

  deploy-staging:
    needs: deploy-dev
    environment: staging-approval   # requires Eng Lead reviewer
    uses: ./.github/workflows/deploy.yml
    with: { environment: staging, auto_promote: false }

  deploy-prod:
    needs: deploy-staging
    environment: prod-approval      # requires Release Manager reviewer
    uses: ./.github/workflows/deploy.yml
    with: { environment: prod, strategy: blue-green, auto_rollback: true }

6. Secrets in the Pipeline

No secret is ever a literal value in workflow YAML. CI reads database URLs, the triage LLM API key, and EHR interface credentials from AWS Secrets Manager via short-lived OIDC federation (GitHub Actions ↔ AWS role assumption, no long-lived AWS keys stored in GitHub). Logs are scrubbed by a redaction filter before being written to CloudWatch, matching the repository's secrets-in-logs rule.

7. Rollback Hook

Stage 13's health-check failure automatically triggers the procedure in Document 5 — Rollback Plan; the pipeline does not wait for a human to notice. See that document for the exact trigger thresholds.

Failure modes this pipeline does NOT handle
A regression in clinical triage quality that stays within latency/error-rate SLIs (the model is fast and "succeeds" but recommends the wrong urgency tier) will not trip these gates. That gap is closed by the triage-quality shadow-evaluation job described in Document 6, section 4 — not by this pipeline. Documenting the gap here satisfies the Failure-First Design requirement to state explicitly what is and isn't covered.

1. Purpose & Scope

Defines how every piece of MedSlot's cloud infrastructure — network, compute, data, cache, CDN, secrets — is declared in version-controlled Terraform and applied through CI, never through the AWS console. Covers module layout, state management, and the change-review process required before any terraform apply can touch a shared environment.

2. Target Architecture

Figure 5 — C4-style context view. Only ehr-adapter and triage-ai-service cross a trust or regulatory boundary; both get the strictest review and canary rollout.

3. Terraform Module Layout

infra/
  modules/
    vpc/              # subnets, NAT, route tables — one per environment
    eks-cluster/       # EKS control plane + managed node groups
    rds-postgres/      # Multi-AZ Postgres, parameter groups, backup policy
    elasticache-redis/ # Redis replication group
    cdn-static/         # S3 + CloudFront for web-frontend
    secrets/            # Secrets Manager entries + IAM access policies
    dns/                # Route53 zones and records
  envs/
    dev/      main.tf  (module calls + dev.tfvars)
    staging/  main.tf  (module calls + staging.tfvars)
    prod/     main.tf  (module calls + prod.tfvars)
  backend.tf   # S3 state bucket + DynamoDB lock table, one state file per env

4. State Management

ConcernMechanism
Remote stateS3 bucket medslot-tfstate-prod (versioned, encrypted at rest with KMS)
LockingDynamoDB table medslot-tf-locks — prevents two concurrent applies
IsolationOne state file per environment; a bad apply in dev cannot corrupt prod state
Drift detectionNightly terraform plan in CI; any non-empty diff against committed code pages the on-call DevOps engineer

5. Change Process

  1. Engineer opens a PR changing a module or an envs/*/*.tfvars file
  2. CI runs terraform fmt -check, terraform validate, then terraform plan, and posts the plan as a PR comment
  3. A second engineer reviews the plan output, not just the diff — a one-line tfvars change can still produce a destructive plan
  4. On merge, CI runs terraform apply against dev automatically; staging and prod require the same manual approval gates as the application pipeline (Document 1)
  5. No one holds standing apply credentials to prod from a laptop — apply only runs from the CI runner's federated role

6. Secrets Management

All runtime secrets (DB credentials, LLM API key, EHR interface certificate) live in AWS Secrets Manager, provisioned by the secrets module but populated with real values out-of-band by a human with break-glass access — Terraform manages the secret's existence and IAM policy, never its value. Pods read secrets via the External Secrets Operator, which syncs them into Kubernetes Secrets at deploy time; nothing is ever baked into an image or a Helm values file.

What this plan explicitly rejects
Any module that creates an RDS instance with publicly_accessible = true, any IAM policy using "Action": "*", and any apply run with a human's personal AWS credentials against the prod account.

3. Parity Rules

What must be identical
  • Container image — the exact tag and hash built once in CI
  • Kubernetes manifest shape (same Deployment, Service, HPA structure — only replica counts and resource limits scale)
  • Database schema version — migrations apply in the same order, same tool (see Document 5 for migration safety)
  • Alert rule definitions (Document 6) — staging alerts to a non-paging channel, same thresholds
What is allowed to differ, and why
  • Instance sizing and replica count — cost control; staging doesn't need prod's peak capacity
  • Data — real PHI never leaves prod; staging and dev use synthetic or de-identified data by compliance requirement
  • External integration endpoints — staging points at the EHR vendor's sandbox FHIR endpoint, not the live clinic system
  • Feature flags — a flag may be on in dev/staging for early testing and off in prod until explicitly promoted

4. Promotion Process

An artifact is promoted, never rebuilt. The pipeline in Document 1 pushes one image to ECR per merge; the same tag is referenced in the Dev, Staging, and Prod Helm values files, changed only by a one-line image.tag bump as it clears each gate. If an environment's deployment manifest ever points at a different image tag than the one that passed the gate before it, that is a parity violation and blocks promotion.

1. Purpose & Scope

Step-by-step procedure for releasing booking-api version 2.4.0 to production using the blue-green strategy from Document 1, stage 12–14. Any on-call engineer should be able to execute this runbook without improvising. Companion to Document 5 — Rollback Plan, which this runbook invokes automatically on failure.

2. Pre-Flight Checklist

  • ☑ Stage 11 approval gate signed off by Release Manager (Document 1)
  • ☑ Error budget headroom confirmed ≥ 20% remaining this month (Document 7)
  • ☑ On-call DevOps engineer and on-call clinical ops liaison both confirmed available for the 30-minute change window
  • ☑ Database migration (if any) is additive/backward-compatible per Document 5, section 3
  • ☑ Change window scheduled outside of Meridian's peak booking hours (7–9am, 5–7pm local)

3. Procedure

  1. Confirm the promoted artifact. 
    kubectl -n medslot-prod get deploy booking-api-blue -o jsonpath='{.spec.template.spec.containers[0].image}'
# Expect: 123456789.dkr.ecr.us-east-1.amazonaws.com/booking-api:2.4.0-7f2c9a1
  2. Deploy the green environment at 0% traffic. 
    kubectl apply -f k8s/prod/booking-api-green-deployment.yaml
kubectl -n medslot-prod rollout status deploy/booking-api-green --timeout=180s
  3. Run automated health checks against green directly (bypassing the router, hitting the green service's internal endpoint): synthetic booking-create, booking-cancel, and EHR-write-acknowledgement transactions. All three must return 2xx with the idempotency key honored on retry.
  4. Shift 10% of production traffic to green via the ALB weighted target group and hold for a 10-minute soak, watching the four SLIs defined in Document 7 in real time on the booking-api-release Grafana dashboard. 
    aws elbv2 modify-rule --rule-arn $RULE_ARN \
  --actions Type=forward,ForwardConfig='{"TargetGroups":[{"TargetGroupArn":"'$TG_BLUE'","Weight":90},{"TargetGroupArn":"'$TG_GREEN'","Weight":10}]}'
  5. If all four SLIs hold (availability, booking-confirm latency, triage hand-off latency, EHR-write success rate — thresholds in Document 7), shift to 50% and hold 10 more minutes, then shift to 100%.
  6. If any SLI breaches during either soak, stop immediately and execute Document 5 — Rollback Plan, trigger "Automated: SLI breach during canary soak."
  7. Keep blue warm for 30 minutes after reaching 100% green traffic — do not scale it to zero yet, in case a slow-burning issue surfaces. 
    kubectl -n medslot-prod scale deploy/booking-api-blue --replicas=0   # only after the 30-minute hold
  8. Post-deploy validation: confirm the release in the #medslot-releases Slack channel with the deployed version, the dashboard link, and the on-call engineer's name. Close the change ticket.

1. Purpose & Scope

No MedSlot release ships without this plan. It defines exactly what triggers a rollback, which version it rolls back to, and why that rollback is always safe for data — the three questions this guide's Discipline section says every release must answer before it ships.

2. Rollback Triggers

TriggerTypeThresholdAction

Booking-confirm p95 latency breachAutomatic> 1,200ms p95 over any rolling 5-minute window during soakPipeline auto-shifts traffic back to blue at 0% green

Clinician or patient-reported critical defectManualAny report of a booking reaching the wrong clinic, wrong urgency tier surfaced to a patient, or a duplicate chargeOn-call declares incident, rolls back regardless of SLI state

3. Target Version

Rollback always targets the last version that completed a full 30-minute soak at 100% production traffic — not simply "one version back." This is tracked automatically by the deploy pipeline as last_known_good, stamped on every successful Document 4 run. For the current release:

Current releasebooking-api:2.4.0-7f2c9a1
Rollback target (last_known_good)booking-api:2.3.6-d81ef44
Rollback commandkubectl -n medslot-prod set image deploy/booking-api-blue booking-api=...2.3.6-d81ef44 && shift traffic to blue 100%
Target rollback time< 90 seconds from trigger to 100% traffic on the target version (blue is kept warm for exactly this reason — see Document 4, step 7)

4. Data Safety

Why rolling back the app never requires rolling back the database
Every migration ships as an additive, backward-compatible change in the release that introduces it (new nullable column, new table, new index). The migration that would remove the old column or constraint only ships two releases later, after the new code has fully soaked in production with no rollback. This means the rollback target version (2.3.6) can always read and write the current database schema safely — there is never a "the old code can't understand the new data" failure mode.

Booking writes are idempotent by construction (client-supplied idempotency key, unique constraint on (idempotency_key) in Postgres, INSERT ... ON CONFLICT DO NOTHING). A rollback mid-request cannot produce a duplicate booking or a duplicate EHR write — a retried request after rollback hits the same unique-constraint guard.

5. Recovery Path if Rollback Itself Fails

If the target version also fails to pass health checks (meaning the regression predates it, or the failure is in a shared dependency like the database), the on-call engineer declares a full incident, routes booking traffic to the static "reduced-capacity" holding page (phone-based booking fallback, published in the clinic ops runbook), and escalates to the Engineering Lead and VP Engineering. This is the dead-letter / manual-intervention path required when automated retries are exhausted.

Frequently Asked Questions

These are the exact questions the Ask assistant is tuned to answer — try typing one into the panel to see it work, or just read them here.

What is MedSlot's booking-confirm availability SLO?

99.90% over a rolling 30-day window, which allows roughly 43.2 minutes of downtime or 84 failed requests per month out of ~84,000. See Document 7 — SLO / Error-Budget Sheet.

What triggers an automatic rollback?

A booking-confirm availability SLI below 99.0% over 5 minutes, p95 latency above 1,200ms over 5 minutes, or EHR-write acknowledgement failures above 1% over 5 minutes — any of these during a traffic-shift soak auto-shifts traffic back to the blue environment. See Document 5 — Rollback Plan, section 2.

Why does MedSlot use blue-green for the API but canary for the AI triage service?

Blue-green gives a fast, binary cutover appropriate for a deterministic API. The AI triage service's failure mode is quality degradation that doesn't trip ordinary error/latency checks, so it earns traffic gradually (10% → 50% → 100%) while quality is actively watched. See Deployment Strategies and Document 1.

What happens if the rollback target version also fails?

On-call declares a full incident, routes traffic to a static reduced-capacity holding page with a phone-based booking fallback, and escalates to the Engineering Lead and VP Engineering. See Document 5, section 5.

How is a release promoted across dev, staging, and prod?

The exact same container image, identified by its immutable tag and hash, is promoted unchanged — only environment-specific configuration changes. It is never rebuilt at any stage. See Document 3 — Environment Strategy and Figure 2.

Where do secrets live, and how are they kept out of code and logs?

In AWS Secrets Manager, synced into Kubernetes via the External Secrets Operator. Terraform manages the secret's existence and access policy, never its value. CI federates to AWS via OIDC rather than storing long-lived keys, and log output is scrubbed by a redaction filter before it reaches CloudWatch. See Document 2, section 6.

What are the DORA metrics, and how does MedSlot score?

Deployment frequency, lead time for changes, change failure rate, and MTTR. MedSlot deploys daily (Elite), has a 3.8-hour lead time (Elite), a 6.1% change failure rate (High band), and a 34-minute MTTR (Elite). See DORA Metrics and Document 8.

Why is MedSlot's availability SLO 99.9% and not 100%?

No real system achieves 100% availability, and chasing that target burns engineering effort that should go toward real reliability work. 99.9% is a defensible, measured target with a tracked error budget — see Monitoring, SLIs, SLOs and Document 7.

How does MedSlot guarantee a booking is never created twice?

Every booking-create request carries a client-generated idempotency key stored with a unique constraint in Postgres, enforced via INSERT ... ON CONFLICT DO NOTHING. A retried request — including one retried mid-rollback — hits the same guard and cannot duplicate the booking. See Document 5, section 4.

What is an error budget, in plain terms?

The inverse of an SLO, turned into a spendable allowance. A 99.9% SLO allows 0.1% of requests to fail; tracking how much of that 0.1% has been used this month turns "should we ship this risky change" into a number instead of a feeling. See Monitoring, SLIs, SLOs, Error Budgets.

What approvals does a release need before reaching production?

Two human gates: Engineering Lead sign-off before staging, and Release Manager sign-off before production — the Release Manager also confirms error-budget headroom before approving. See Document 1, stage 8 and 11.

What is NOT covered by the automated pipeline gates?

A triage recommendation that is fast and technically successful but clinically wrong — it won't trip latency or error-rate gates. That gap is covered separately by the weekly shadow-evaluation process in Document 6, section 4, which is explicitly named as a known limitation of Document 1's pipeline.

How does Terraform state stay safe with multiple engineers working at once?

Remote state in a versioned, encrypted S3 bucket, with a DynamoDB table enforcing a lock so only one apply can run at a time; one state file per environment keeps a bad dev apply from ever touching prod state. See Document 2, section 4.

Why can the application always roll back without a database rollback?

Migrations ship in two steps: an additive, backward-compatible change first, and only once the new code has fully soaked does a second release remove the old column. The rollback target can therefore always read and write the current schema. See Document 5, section 4.

Which SLO is closest to running out of budget right now?

EHR-write success rate, at 79% of its monthly error budget consumed with 9 days left in the window — inside the 50–89% policy band, which requires Release Manager sign-off on any EHR-adapter feature until the next reset. See Document 7, Figure 8 and section 3.
