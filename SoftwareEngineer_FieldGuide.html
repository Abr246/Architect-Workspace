The Software Engineer Field Guide

You are training to become an AI Solution Architect. You will not spend your career hand-writing every service, model, and test — AI will draft most of that code in seconds. Your job is to direct, evaluate, and approve what the AI produces. This guide teaches the roughly 20% of software engineering discipline that makes that judgment possible, then shows what "good" looks like by building a complete, realistic engineering package for one example feature end to end.

Working example

The example initiative: KitchenPulse

Every document in this guide is built against one concrete, believable feature so you can see how each engineering concept plays out in practice — not as an abstract template, but as real code and real documents an AI Solution Architect would have to review and sign off on.

The organization

Trestle Restaurant Group operates Copper Kettle Kitchen, a 34-location fast-casual chain across Washington, Oregon, and Idaho, serving roughly 2.4M orders per year across dine-in, online, and third-party delivery channels.

The problem

During peak hours (11:30am–1:30pm and 5:30–7:30pm), the average ticket-to-serve time runs 14.2 minutes against a 9-minute service-level target, with 31% of tickets missing that target entirely. The expo station manually re-sequences tickets by eye across grill, fry, and salad stations — hot items sit under heat lamps going soggy while cold items get rushed and assembled wrong. Remakes from missed timing cost the chain an estimated $740K/year in food waste.

The initiative

KitchenPulse — an AI-assisted Kitchen Display & Order Prioritization System. It ingests orders from the POS (Toast), the in-house ordering app, and delivery aggregators (DoorDash, UberEats); predicts per-item prep time with a trained model; computes a dynamic priority score per station so items finish together; and pushes live-reprioritized queues to Kitchen Display Screens, with expo override.

Scope

A 4-month build (September–December 2026), piloted at 3 locations, then rolled out to all 34. Sponsor: VP of Restaurant Operations. Business owner: Director of Culinary Operations.

Why this example

Why software engineering exists

LLMs are probabilistic. A kitchen running on a probabilistic system — one that is usually right — is a kitchen that occasionally sends a well-done burger to the fryer queue and nobody notices until the ticket times out. Software engineering exists to wrap probabilistic reasoning in deterministic, testable, reviewable structure: the same input produces the same output, every time, and when it doesn't, there is a defined way to find out why.

As an AI Solution Architect, generative AI will draft KitchenPulse's services, its tests, and its pull requests in seconds. That collapses the writing cost of software engineering to nearly zero — and raises the judgment cost to nearly everything. You are no longer graded on how fast you can write a service. You are graded on whether you can look at AI-generated code and know, specifically, whether the interface is honest, whether the failure path is handled, and whether the tests actually assert behavior or just execute lines.

The 20% that matters
You do not need to become a full-time software engineer. You need the ~20% of the discipline that lets you direct the AI ("build PrepTimePredictionEngine with an explicit timeout and a documented fallback"), evaluate its output ("this catch block swallows the error silently — reject it"), and approve what gets merged. That 20% is what the rest of this Foundations section teaches.

Technical design documents

A Technical Design Document (TDD) is written before the first line of implementation code, not after. It states the problem, the chosen approach, the alternatives considered and rejected (with reasons), the module breakdown, the data model, and the risks — so that disagreement happens on a page, cheaply, instead of in a 2,000-line pull request, expensively.

Why it matters to an architect

An AI can generate a working KDS service in minutes. It cannot tell you, unprompted, why a WebSocket push model was chosen over polling, or what happens when the prep-time model is unavailable at 12:15pm on a Saturday. That reasoning has to be captured somewhere a human can review it before code ships.

KitchenPulse's TDD

See Document 1 for the full design: chosen approach (event-driven, WebSocket push), two rejected alternatives, a 7-module breakdown, an ERD, and a sequence diagram for the order-to-served flow.

Reviewer's flag
If an AI hands you code with no design document behind it, the design decisions are hidden inside the implementation, not reviewable as decisions. Ask for the TDD first, especially for anything touching real-time delivery to hardware in a live kitchen.

Modularity & separation of concerns

Modularity means each unit of code does one job and exposes a narrow, explicit way for other units to ask it to do that job. Separation of concerns is the discipline that keeps those jobs from blurring together — a module named orderIngestionService.ts should not also decide kitchen-station priority; a module named priorityQueueEngine.ts should not also format a WebSocket payload.

Review habit
When an AI hands you a service, ask what its one responsibility is, in a single sentence. If the answer needs "and," the module is doing two jobs and should be two modules. See the KitchenPulse Module Design for seven modules, each with exactly one stated responsibility.

Interfaces & contracts

An interface is the typed shape a module exposes to the rest of the system. A contract is the interface plus the rules that govern it: what inputs are valid, what output is guaranteed, and what errors can be thrown and under what conditions. A function signature without documented errors is half a contract — it tells the caller what success looks like and leaves failure to be discovered in production.

Why it matters to an architect

AI-generated code routinely gets the happy-path signature right and leaves the error contract implicit. predict(item, stationState) tells you nothing about what happens when the model registry is down — predict(item, stationState): Promise<PrepTimeEstimate> throwing a named ModelUnavailableError does.

KitchenPulse's contracts

Every one of the seven modules in Document 2 lists its inputs, its output type, and every named error it can throw — the contract an AI Solution Architect signs off on before the module ships.

Clean code & naming

Code is read far more often than it is written. Clean code optimizes for the reader, not the writer: names that reveal intent (waitSeconds, not x), functions short enough to hold in working memory, and structure that doesn't require reading three other files to understand what a line does.

The naming test
If you have to open a function's body to know what it does, the name has failed. computePriorityScore(waitSeconds, stationLoad, slaBudgetSeconds) passes; calc(x, y, z) does not. See Coding Standards for KitchenPulse's full naming convention table.

Version control: branching & code review

Version control is the record of every change and why it was made. Branching isolates in-progress work from the deployable main branch; code review is the gate that catches what the author couldn't see in their own diff — and, increasingly, what an AI generated but didn't fully justify.

The non-negotiable rule
main is protected. Every change reaches it through a pull request, reviewed by a human, passing CI. No branch skips this because the author (human or AI) was confident. See the KitchenPulse Branching & PR Workflow for the full trunk-based model in use.

The testing pyramid

The testing pyramid describes the healthy shape of a test suite: many fast, cheap unit tests at the base (~70%), fewer integration tests touching real dependencies in the middle (~20%), and a thin layer of slow, expensive end-to-end tests at the top (~10%). A suite that inverts this — more browser tests than unit tests — is a process violation: it's slow to run and painful to diagnose when it's red.

Common AI-generation failure
AI often over-produces end-to-end-style tests because they read as more "impressive," and under-produces the boundary and failure-path unit tests that actually catch defects cheaply. See the KitchenPulse Test Plan for a suite that holds the 70/20/10 shape.

Technical debt

Technical debt is a shortcut taken deliberately (or accidentally) that makes future change more expensive — like a 900-line service that should have been split into three modules. Debt itself isn't always wrong; taking it on without naming it is. A healthy team logs the debt, states the interest it's accruing, and pays it down when the file is touched again.

The rule this repo uses
Existing oversize files are grandfathered until touched; each subsequent modification to that file is an opportunity to extract and split — the exact rule KitchenPulse's Coding Standards apply to its own codebase.

DRY & SOLID (lightly)

DRY (Don't Repeat Yourself) says duplicated logic should be lifted into one place — but only once it has appeared three times; two occurrences can be coincidence, not a pattern worth abstracting. SOLID is five lightweight design habits: Single Responsibility (one reason to change), Open/Closed (extend without rewriting), Liskov Substitution (a subtype must honor its parent's contract), Interface Segregation (small, focused interfaces beat one giant one), and Dependency Inversion (depend on an abstraction, not a concrete implementation).

Where it shows up in KitchenPulse

PrepTimePredictionEngine depends on a ModelClient interface, not directly on the Azure ML SDK (Dependency Inversion) — so swapping model hosting later doesn't touch the six modules that call it.

The trap to avoid

SOLID is a set of habits, not a checklist to satisfy on every function. An AI that wraps a single 10-line utility in three abstraction layers "for SOLID" has made the code harder to read, not more principled.

Error handling & failure-first design

Design the failure path before the happy path. Every external boundary — a model inference call, a POS webhook, a WebSocket push to a kitchen screen — needs an explicit timeout, a documented retry strategy, and a defined fallback or fail-fast behavior. A silent catch (e) {} is not error handling; it's a decision to lose information, made invisibly.

Forbidden pattern
Catching an error and continuing without logging its class and context. When KitchenPulse's model-inference call times out, the code must say so — error_class: "TimeoutError", not silence, and not a generic Error swallowed and forgotten. See the Code Review Checklist, Idempotency & Failure-First section.

Engineering KPIs

Four numbers tell you more about an engineering team's real health than a burndown chart alone: test coverage (is behavior actually asserted, not just executed), PR cycle time (time from open to merge — a proxy for review friction and PR size discipline), defect trend (issues found in review or production over time), and deployment frequency (how often working code actually reaches users).
